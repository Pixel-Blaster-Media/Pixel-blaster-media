# Tenant listing and admin search regression

Run from `booking/`: `npm run test:postgres:tenant-search`.
Requires PostgreSQL **17** binaries (`POSTGRES_BIN` can override the Homebrew default). The runner creates a fresh temporary cluster, listens only on a temporary Unix socket, never reads project connection credentials, and stops/deletes the cluster in `finally`. It never targets Supabase or production.

The minimal bootstrap explicitly grants authenticated API-role DML and gives `service_role` BYPASSRLS. Original listing policies/helpers come from the canonical tenant migration, and the original listing table from the preserved bootstrap. Fixtures prove the foreign-property exploit both as realtor and tenant admin, and the existing-listing unique-index counterexample. Exact candidate SQL then proves policy rejection, structural service-role rejection, parent mutation integrity, optional-booking deletion compatibility, atomic failed migration on historical poison, and apply/rollback.

Search fixtures cover 1,200 bookings (600 active/600 delivered), 350 additional realtor profiles, two tenants, search beyond the former 500/300 caps, complete owner totals, all-page UUID cursor traversal without gaps/duplicates, literal wildcard input, foreign-tenant denial, non-admin denial, and archived-admin denial. Search uses authenticated, explicitly authorized RPCs. `--red` intentionally fails on the original exploitable policies; `--search-red` intentionally fails by executing the old after-500 search algorithm on the same fixtures.

The browser pages display 50 rows plus explicit next/first-page navigation; SQL fetches one sentinel row. SQL orders the active view by unscheduled-request priority, scheduled_at ASC NULLS FIRST, created_at DESC, then UUID. Other job views retain schedule/creation order without the active-only priority. Realtors retain full_name ASC NULLS LAST, email ASC, then UUID. Ordering is applied before the limit and repeated in JSON aggregation. Each row carries an `_cursor` JSON object with the complete ordering keys; the route validates its shape, UUID and timestamps and preserves PostgreSQL microseconds verbatim. Malformed and legacy UUID-only links restart at page one. Search/filter links reset the cursor. A cursor is not a cross-request database snapshot: inserts or edits before the cursor require returning to the first page. Search and counts are database-complete, not derived from those windows. Full-history count failure is a page error, never a fake zero.

`tenant-search-order.sql` checks exact ordered traversal of 160 jobs and 160 realtors across null and duplicate sort keys. Every existing service/catalog display label and raw slug is exercised against 51 PostgreSQL rows; a Node parity test evaluates `labelForService` and compares all known mappings with SQL. The retained legacy add-on labels are also tested. The SQL mapping is complete and checked, not a partial unchecked copy. The earlier UUID-only traversal is now composite-key traversal.

The search migration has not been released in this lane; its reviewed candidate definition is corrected in place. Its RPC signatures now take JSONB cursors with unchanged authenticated-only execution grants. If an earlier candidate was applied elsewhere, stop and reconcile the ledger/old UUID signatures explicitly rather than replaying this file.

Migration files are additive and must be applied transactionally in version order **before** deploying the consuming application. Invalid historical listing links abort rather than being rewritten/deleted. This suite is not a full bootstrap, live-ledger check, PostgREST HTTP test, or production cardinality/exploit test. Reconcile the remote migration ledger, review historical integrity and exact migration SQL, and obtain release approval separately. Never use `--include-all` to ship these changes.
